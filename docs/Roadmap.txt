Agreed plan: comparison types, hashing, folder snapshots (decided 2026-11-07)
==============================================================================

Order (each step depends on the one before)
 1. History: DEL on a hovered drop-down entry removes it (no confirmation).
 2. Comparison type setting (Settings > Global Options) + "Ignore file extensions".
 3. Hashing: hashes stored on snapshot nodes, per-pane Hash button, progress, cancel.
 4. .fss folder snapshot: Save Snapshot, load via Select Directory / drag-and-drop.
 5. Snapshot mode: file ops disabled, "File Parent" -> "Item Parent", Select buttons
    verified for snapshot-vs-live and snapshot-vs-snapshot.

Comparison types (Global Options, shared by both panes)
 - Name, size and date: the CURRENT behavior. Default, and the fall-back whenever
   hashes are unavailable (unhashed files, snapshot saved without hashes, snapshot
   whose comparison type conflicts with the current one).
 - Hash value (algorithm selectable: MD5, SHA-1, SHA-256 [default], BLAKE2b).
 - Fingerprint: lossy partial hash = file size + start chunk + end chunk (chunk sizes
   settable in kB; whole file hashed if smaller than both chunks combined).
 - "Ignore file extensions" (applies to the name-based type only): files match or
   don't match by name without extension; size and dates are NOT compared. Any
   matching counts as matching, even if several files match in the other folder.

Hash/fingerprint pairing
 - Files are paired within the same relative folder by CONTENT, ignoring file name
   (a renamed file still matches; a file moved to another folder does not).
 - Pass 1: equal hashes pair one-to-one (identical names preferred on ties).
   Pass 2: leftover files with the same name = "Content differs". Rest = missing.
 - Folders still pair by name only.
 - Synchronize Views / selection mirroring use the same counterpart rule.
   Move/Copy across stay name-based (they act on the real filesystem).
 - Equal hash = "matching" even if dates differ. Different hash keeps the
   newer/older/larger/smaller tags; if size and date are equal -> "Content differs".
 - Unhashed files (hash types only) get their own colors: Comparison Type Colors
   table, new row "Unhashed" (File/Folder Fg/Bg).
 - Settings > Comparison Type Colors: row "Diff Folders" renamed "Content differs";
   gains File Fg/Bg swatches (Folder Fg/Bg keep working as-is).
 - Select button "Diff Folders" -> "Diff Items" (folders and "Content differs" files).

Hash button (per pane, before "Clear view"; colors in Button Colors table)
 - Disabled when the active type uses no hashes, and on snapshot panes.
 - Recursive Folder Selections on: hash everything in the pane. Off: hash only what
   is visible (expanded). Press again after expanding; already-hashed files are
   skipped (cache keyed by path+size+mtime; invalid after Refresh change or when
   algorithm / chunk sizes change).
 - Enumerate first (busy bar), then progress bar by bytes. Cancel via the pane's
   Cancel button; hashes already computed are kept.

Folder snapshot (.fss, JSON)
 - Stores: format version, comparison settings used, original root path + name,
   creation time, tree of names + metadata (size, dates) + hashes if present.
 - Recursive Folder Selections on: full tree. Off: expanded folders' contents only;
   unexpanded folders get a dummy child "Content not scanned" (+ size/item count).
 - Save Snapshot button next to Select Directory (own row in Button Colors table).
   In hash mode with no hashes: prompt Hash now / Save without hashes / Cancel.
   Also works on a pane already showing a snapshot (re-save).
 - Select Directory and drag-and-drop (FLV or Statistics View) load .fss files.
 - Snapshot pane: Hash, file ops, clipboard, Make New Folder, Open/Properties,
   drag-out disabled; cross-pane Move/Copy disabled if either pane is a snapshot.
   "Clear view" clears it and returns the pane to normal.
 - Loading a snapshot whose comparison type differs from the current one: prompt to
   adopt the snapshot's settings; if declined, fall back to Name/size/date and show
   a red status message (until the next status message). Red = Misc Colors row.
 - History drop-down: snapshots listed by .fss file name (full path as tooltip),
   own text color (Misc Colors, default light gray, no Bg); live-folder entries get
   a color setting too. A small label above the combo shows the stored original
   path + root name for snapshots (hidden for live folders).

Status 2026-11-07: steps 1-5 implemented and merged. Where the result differs
from / extends the plan above:
==============================================================================
 - Pairing is NOT one-to-one: every file whose content exists in the other
   folder is "matching", however many duplicates either side has. A folder whose
   same content occurs a different number of times on each side is "Content
   differs". "Only first part of file name" added as a second name-matching
   option (mutually exclusive with "Ignore file extensions").
 - Synchronize Views mirrors file selection by the comparison: by content for hash
   types, by name stem for the two name options; several matches are all selected.
 - Settings > Options (was Global Options; block placed after Theme): "Multi Select
   matching files in same pane" (hash types) selects identical files when a file
   is selected by hand (click, Ctrl/Shift-click, drag); "Same folder only" limits
   that to the file's folder, else pane-wide (and mirrored pane-wide in the other
   pane). Both persisted, default on.
 - Snapshot hashes made with other settings than the current ones (or no hashes
   at all), with a hash type selected: NOTHING is compared (no fall-back to
   name/size/date any more). Items show the "Hashed, not compared" colors (new
   Comparison Type Colors row, also used for a hashed pane with nothing to
   compare against / Dual Pane off), a warning shows in the status label, and the
   comparison Select buttons are disabled.
 - Larger/Smaller/Newer/Older Select buttons are disabled while files are
   compared by content.
 - "File Parent" renamed "Item Parent": adds the parent of every selected item
   (files and folders), one level per press, additively.
 - Disabled buttons (all bevel-styled ones) fade toward the GUI background.
 - Select buttons read only the cached snapshot data (no disk access); snapshot
   panes are read-only (File Op, Clipboard, Cut/Copy/Paste, Open/Properties and
   drag-out disabled, also in the narrow layout).

Plan: persistent hash cache (decided 2026-11-18, all five steps implemented, see status below)
==============================================================================

Idea: make the existing in-memory hash cache (diff_engine._attach_cached_hash,
hash_ops._hash_cache / _hash_cache_by_inode) survive restarts, so hashes are not
recomputed. It is NOT a snapshot view: the pane always shows the live folder.

Setting (Settings > Options, global, shared by both panes)
 - "Cache hashed folders". Tooltip: only hashed and fingerprinted items are cached.
 - Name, size and date never reads or writes the cache; it behaves as today.
 - Default off. Turning it off leaves the cache file untouched.

What is stored / used
 - Only hashed and fingerprinted files, keyed by path, with size, mtime and the
   digest per comparison key (type, algorithm, chunk sizes). Several keys per file
   are kept (most recent 3); Rehash / Clear cache reset them.
 - Entries are valid only while size and mtime still match (as the in-memory cache).
 - NO ghosts: cached files that no longer exist live are ignored and dropped
   when the cache is next written for that folder (only folders actually scanned,
   never after a failed scan). No cache-as-offline-view; offline folders are
   covered by explicit .fss snapshots.
 - Read once into RAM when a folder loads; switching comparison type re-attaches
   hashes from RAM without a disk rescan.

Colors (Comparison Type Colors table, hash modes only)
 - New row "Changed since cached" (File/Folder, Fg/Bg): a cached path whose size
   or mtime differs. Wins over "Unhashed".
 - "Unhashed": no usable entry for the current key (new file, or cached only
   under another key).
 - Folders: derived from contents like Unhashed (any changed file inside = Changed,
   Changed > Unhashed); the folder's own mtime is ignored.

When the cache is written (opening a folder writes nothing)
 - Hash / Rehash: flushed about every 30 s while hashing and at the end, so Cancel
   or a crash keeps the work. Progress by bytes already exists.
 - DirComp move, rename, delete: move/rename carry the hash to the new path
   (folders re-key everything below), delete removes entries. Copy: the new file
   gets the source hash if destination size and mtime equal the source's.
 - Pruning of missing files happens on these writes (see above).

Buttons
 - Hash: unchanged, hashes only the delta (unhashed or changed files).
 - Rehash (new, per pane next to Hash, own row in Button Colors): same scope as
   Hash (Recursive Folder Selections on = all files, off = visible only). Discards
   ALL stored digests (every key) for those files and recomputes under the current
   key only. Confirmation dialog first. Reports how many files hashed differently
   although size and date were unchanged.
 - Settings: "Clear cache" button (wipe everything).

Storage
 - One SQLite file (stdlib sqlite3) rather than one file per folder: Cache/hashes.sqlite
   in the program folder, falling back to the user cache dir (XDG cache /
   %LOCALAPPDATA%) if not writable. Add Cache/ to .gitignore.
 - Atomic/WAL writes, format version, corrupt file = rebuild, single writer
   (both panes may show the same folder). The cache holds file names and hashes
   of browsed folders; mention in the tooltip.
 - Paths normalized (case on Windows). Moving a folder outside DirComp loses its
   entries (renames within a session still match by inode).

Explicitly NOT doing: ghost rows, size-based pre-filtering of what to hash, a
"Verify" button (Rehash covers it).
